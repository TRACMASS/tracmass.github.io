Reading in Variables (UNDER CONSTRUCTION - draft)

Introduction

TRACMASS can read in various variables, such as, various levels of velocity field resoluiton and tracers variables, like temperature and salinity. The function to read in variables is called every global loop timestep (intrun). However, the user has high flexability avilable when it comes to input data frequency reading in.

In this chapter we will ilustrate the basics of file reading and the general logic behind it. All of these actions are done in the read_field.F90 file, which is located in the project folder (read more about the project folder here). Furthermore, instead of writing the file yourself from scrathc, it is recommended to use one of the files provided and modify it to your needs. This way you will save time and sanity.

Structure of read_field.F90

the file is called once before starting the TRACMASS loop interations, and every loop step. More info on the 3 thingy in normal language

In general, the file will contain a section where all the variables are read into TRACMASS, and possibly some data processing that needs to be done on the data, so that TRACMASS can comfortably work with it. As an example can be considered velocity field data on an Arakawa A-grid, instead of the C-grid, that TRACMASS uses. Thus, the file can be seperated in two parts - data reading and data transformatoin. As there is no standardized method for data saving from model simulations, you will most likeley need to modify some of the data.

This is a list of the data that is mandatory to have:

  • uflux - implies a velocity field and respective grid cell's wall area
  • vflux
  • wflux (if explicitly stated)
With this data, it is possible to calculate trajectories in the model. But, it is also possible to add sea surface height (SSH), bathymetry, and tracers.

Reading in velocity fields

Even though the horizontal velocity or flux fields are mandatory, the subgrid levels of these fields are optional. Thus, ueul_name and veul_name must be defined, while the other ones can be left empty or completely ommited from the namelist file. An example of setting up the namelist for TRACMASS to read in the velocity field is the following:

In this example we have our velocity data saved in the same file as our tracers, thus, the tGridName, uGridName, and vGridName fields have been left blank. In this case, these fields could have been completely been omitted.

Here we have also defined the the location of our file, the various parts of the file format to merge it together and finally start the process of reading in the files. For this, there are two functions that you will use for this - get2DfieldNC and get3DfieldNC. As can be seen, both have the same inputs.

  • fieldFile - file name with the path to the file
  • varName - variable of the .nc file that will be read in
  • start3D/start2D - the starting index of reading in the file in 4 dimensions [x, y, z, t]
  • count2D/count3D - the number of indexes to read 4 dimensions [x, y, z, t]
  • stcase - format in which the array is saved, refer to the documentation

This is how the code would look in our read_field.F90 file. In this case we read in the whole spacial domain and only one timestep, in this case the first time step, as our .nc file starts with index=1.

{{ site.data.tutorial_examples.read_field_read_file }}

Great advantage of TRACMASS structure is that the read_field.F90 file is called at the begining of each loop and at the very top of the file time stepping is enabled with function swap_time()

There is high flexability available to the frequency of reading in the velocity data, thus great care should be taken to ensure the read_field.F90 file algorithm matches the time stepping definitions in the namelist file.

Reading tracers

Reading in tracer data is essentially the same as the velocity field data. It's good practice to include the tracers in a IF-ELSE logical statment, which would allow to read in the tracer data only when l_tracers is set to .TRUE.. This provides more flexablity of the data. Furthermore, care should be taken when setting up the tracers, as they have 2 options available - 'read' and 'compute'.

Next, it is necessary to understand the frequency of the general loop and also the time resolution of the tracer data set itself. For example, if we have a velocity field data with 15min resolution, we might want to read it in every 15 minutes, while a tracer, such as temperature, might have only hourly resolution. For this, purpose, it is useful to use variables, such as currYear, currMon, currDay, currHour, currMin, currSec. For example, this is how conceptually the synthax would look like:

Note:
It is recomended to use read_field.F90 file as a template for reading in the necessary data. The main aspect that should be changed is the frequency and at which points in time what data should be read in by the file.
