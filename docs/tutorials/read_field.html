Reading in Variables (UNDER CONSTRUCTION - spelling and grammar check)

Introduction

TRACMASS can read in various variables, such as, various levels of velocity field resoluiton and tracers variables, like temperature and salinity. The user has high flexability avialable when it comes to input data reading. However, the process is not straighforward, thus, a short guide is presented here in hopes to clear up some of confusion.

In this chapter we will ilustrate the basics of file reading and the general logic behind it. This chapter is mainly written for the setup of read_field.F90, but the methods are same for setup_grid.F90 (and kill_zones.F90). ALl of these files are located in the project folder (read more about the project folder here). Furthermore, instead of writing the algorithm yourself from scrathc, it is recommended to use one of the files provided and modify it to your needs. This way you will save time and your sanity.

Note:
It is recomended to use read_field.F90 file as a template for reading in the necessary data, by finding a file that fits most to your project's needs and modifying it, where necessary.

Structure of read_field.F90

The function to read in variables is called every global time iteration. In general, the file can be split up in two parts - data reading into TRACMASS and data transofrmation/processing so that the data fits TRACMASS' framework. As an example can be considered velocity field data on an Arakawa A-grid. TRACMASS carries out its calculations with data distributed on Arakawa C-grid, thus, to accurateley run the simulation, it is necessary to transform the data set from Arakawa A-grid to C-grid. As every dataset will differ, there is no standardized method for reading in the data from global climate model simulations, thus, you will most likeley need to modify some of the data for TRACMASS to work with it in the read_field.F90 file.

This is a list of variables that is mandatory to be populated:

  • uflux - volume/mass flux through a grid's face in x direction
  • vflux - same as uflux but in y direction
This is the bare minimum data needed in read_field.F90 file for calculating trajectories.

Note:
The file read_field.F90 is called every global time step and at the very top of the file, subroutine swap_time()is called that does the velocity and tracer field time stepping for you.

Reading in velocity fields

Even though the horizontal velocity (or flux fields) are mandatory, the subgrid levels of these fields are optional. Thus, ueul_name and veul_name must be defined, while the other ones can be left empty or completely ommited from the namelist file. An example of setting up the namelist for TRACMASS to read in the velocity field is the following:

{{ site.data.tutorial_examples.read_field_velocity_namelist }}

In this example we have our velocity data saved in the same file as our tracers, thus, the tGridName, uGridName, and vGridName fields have been left blank. In this case, these fields could have been completely been omitted.

Here we have also defined the the location of our file, the various parts of the file format to merge it together and finally start the process of reading in the files. For this, there are two functions that you will use for this - get2DfieldNC and get3DfieldNC. As can be seen, both have the same inputs.

{{ site.data.tutorial_examples.read_field_get_file_function }}

  • fieldFile - file name with the path to the file
  • varName - variable name that will be read in from the file
  • start2D/start3D - the starting index of reading in the file in 4 dimensions [x, y, z, t]
  • count2D/count3D - the number of indexes to read in 4 dimensions [x, y, z, t]
  • stcase - format in which the array is saved, refer to the documentation

This is how the code would look in our read_field.F90 file. In this case we read in the whole spatial domain and only one timestep, in this case the first time step, as our .nc file starts with index=1.

{{ site.data.tutorial_examples.read_field_read_file }}

There is high flexibility available to the frequency of reading in data, thus great care should be taken to ensure the read_field.F90 file algorithm matches the time stepping definition in the namelist file of the global time step.

Reading tracers

Reading in tracer data is essentially the same as the velocity field data and it is recomended to use the code for tracer reading found in project NEMO. Every iter iteration, the file reads in the next dataset or computes it. If it neads to read it, the code checks if the dataset is 2D or 3D and reads the according shape into the file. Finally, the dataset is saved in the correct timestep and can be used for future calculations.

{{ site.data.tutorial_examples.read_field_tracers }}

Next, it is necessary to understand the frequency of the general loop and also the time resolution of the tracer data set itself. For example, if we have a velocity field data with 15min resolution, we might want to read it in every 15 minutes, while a tracer, such as temperature, might have only hourly resolution. For this, purpose, it is useful to use variables, such as currYear, currMon, currDay, currHour, currMin, currSec. For example, this is how conceptually the synthax would look like:
